## Studio: пять настоящих клиентов

1. `rojo build social-tests.project.json -o DoubleLife-M5-tests.rbxlx`. Открыть файл, Server and Clients, запустить **пять** клиентов. Допустимо начать с одного, дождаться `M5 WAITING PASS` и добавить четыре; если уже запущено пять, сообщение о добавлении четырёх игнорировать.
2. Драйвер удерживает Waiting до окончания проверки первого профиля и готовности пятерых. Тестовый Countdown 300 с позволяет запустить окна; затем драйвер запускает раунд. Production Countdown 12 с, тестового барьера там нет.
3. Драйвер использует реальные `ProximityPrompt:InputHoldBegin/End`, RemoteEvent/RemoteFunction, пять настоящих Player/Character. Позиции задаются тестовым клиентом для воспроизводимости: это интеграция взаимодействий, не непрерывный ручной маршрут и не проверка сетевого античита.
4. Сценарий: попытка выдачи чужой ролью/издалека → персональный допуск → считыватель/дверь → экспонат/след → передача по согласию → доставка → ложный след → Council pause → контекстный знак → независимое окно шпиона → сейф/выход/Results.
5. На Results все пять видят разрешённую публичную косметику. Fake ProcessReceipt получает потерю ответа после commit и повторные вызовы; реальный клиент использует один заряд, повторный чек не восстанавливает его. Перезапускается жизненный цикл профиля M4.1 на том же Player/UserId.
6. Во время 60-секундной паузы для обзора нажать **H** (свернуть Results), отдалить камеру, **K**; проверить цены «недоступно», возможность скрыть эффекты, публичный титул над аватаром. Дождаться `M5 STUDIO PASS` после сброса.
7. По сообщению `M5 EIGHT CLIENTS` добавить **три** клиента в течение 300 с. Драйвер запускает следующий раунд с восемью, проверяет две шпионские и две агентские роли, отключает одного шпиона настоящим `Player:Kick`, проверяет продолжение Active и вынос досье вторым через настоящие prompts. Дождаться `M5 EIGHT CLIENTS PASS`, затем Test → End Session. Если расширение не проводится, остановить после основного PASS и явно не заявлять 8-клиентный прогон.

Тестовые ID 101/202 существуют только в fixture; fake adapter не вызывает Roblox. Клиенту в fixture отправляются ID=0, поэтому даже запрос цены не обращается к реальному товару. Studio UserId преобразуется в синтетический положительный ID только внедрённой тестовой функцией. В production эта подмена запрещена. Профили, чеки и аналитика находятся в памяти процесса, реальных списаний нет.

Уход обоих шпионов и timeout дополнительно проверяются pure-тестами. Если 8+ запуск физически не состоялся, записать ограничение в VALIDATION; матричные тесты не выдавать за многоклиентный прогон.

## Долговечность чеков

`Commerce_<UserId>` в отдельном `DoubleLife_Commerce_v1` хранит **вместе**: неизменяемую карту PurchaseId→ProductId, баланс зарядов, карту идентификаторов использования и ожидающий косметический показ. Один UpdateAsync атомарно проверяет чек и начисляет заряд. Ни игровая lease, ни 64-entry ledger M4 не участвуют. Конкурирующие серверы работают с последней записью, не сохраняют локальную копию целиком. `PurchaseGranted` возвращается только по подтверждённой записи с точным PurchaseId/ProductId; любой сбой — `NotProcessedYet`.

Записи никогда не обрезаются. Лимит 4 000 покупок и 4 000 использований на аккаунт; ID ≤128 байт. Это менее 4 MB даже при максимальных ID с JSON-экранированием обычных символов; управляющие символы запрещены. Магазин прекращает предложения за 100 покупок до лимита; внешние/ожидающие чеки при полном ledger остаются `NotProcessedYet`. До достижения потолка нужна миграция без удаления tombstones и без сброса баланса. Откат на старую схему/восстановление только одного поля запрещены. Это ограниченная по ёмкости **вечная память принятых чеков**, не обещание неограниченного числа покупок.

Использование заряда сохраняет ожидающий эффект в той же транзакции. Если процесс оборвался до/во время показа, ожидание сохраняется и повторяется в социальной фазе без второго списания. Подтверждение завершения после четырёх секунд отдельное и идемпотентное. При потере ответа возможен повтор самого визуального показа; оплаченный заряд никогда не начисляется повторно. На сервере один показ раз в 10 с; на аккаунте перерыв 60 с. Active/Council не запускают и не продолжают визуальный эффект. Нет преимуществ, свободного текста, случайного платного содержимого или обмена коммерческими правами.

## Аналитика и границы

Серверный конечный список: Join, SessionSeconds, MatchStarted, FirstMatch, RepeatMatch, Waiting/Countdown/Active/Council/Results, Win/Loss, ShopOpen, Offer, Purchase. Значения числовые, без ролей, PurchaseId, баланса, произвольного текста или внешних идентификаторов. ShopOpen/Offer не чаще 15 с; остальные не чаще 1 с. Studio использует stub; ошибки AnalyticsService не мешают игре. Счётчик Purchase — диагностический, не финансовая книга: при повторной доставке на новый сервер возможен повтор события. Источник финансовой отчётности — Roblox и сохранённый ledger.

После запуска измерить D1/D7, длительность сессии, завершение/повтор матчей, shop→prompt→purchase, платящую долю и выручку на активного. Сейчас никаких значений этих метрик или рабочего dashboard не заявляется. Полные ручные матчи, балансировка, мобильная производительность, большая карта и финальные ассеты отложены до M6–M8.
