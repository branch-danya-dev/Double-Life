# M4 — сценарии проверки

## M4.1: восстановление при повторном входе

База: `3850e3c982e136dc641bffdc66cfc464580df94c`, ветка `fix/m4-profile-reconnect-recovery`. Все прежние **524** assertions остаются без изменения; новый `luau tests/reconnect.luau` добавляет **54**, всего **578**. CI также анализирует чистый `ProfileSessions`, компилирует все Luau и собирает production, полный M4 fixture и отдельный короткий reconnect fixture.

Регрессия в начале `tests/reconnect.luau` написана и запущена до исправления: три ошибки close → load того же UserId с новым токеном. На M4 она падает, получая `Unavailable / old-connection`; на M4.1 получает `Ready / new-connection`. [Исходный сбой](evidence/M4.1-before.log), [итоговые проверки](evidence/M4.1-automated.log).

Дополнительные случаи: release после timeout; запись до потери ответа; повтор покупки; сохранность XP/мастерства/истории/экипировки; запрет устаревших enqueue/flush/close; чужая активная lease; истечение lease и распознавание подтверждённых receipts/sequence; явные unconfirmed для оставшихся операций; обычная награда следующего раунда. Детерминированный coroutine scheduler запускает **производственный ProfileSessions**, воспроизводя второй/третий вход, уход во время Loading/retry, неизвестный исход acquisition, зависший вызов дольше срока close, постоянный outage, автоматическое восстановление после чужого release, параллельные remove/shutdown и отмену callbacks при shutdown. Проверяется честный отказ BindToClose и отсутствие defaults-overwrite.

### Короткая интеграция в Studio

1. `rojo build reconnect-tests.project.json -o DoubleLife-M4.1-reconnect.rbxlx`.
2. Открыть сцену, Test → Start Test Session → Server and Clients; добавить **одного** клиента. Не подключать Rojo к другим проектам и не включать API Services.
3. Runner создаёт **синтетический** ранее заработанный профиль в fake adapter: 75 XP, 28 жетонов, 40 XP шпиона, одна запись истории. Это подготовка данных, не сыгранный матч. Реальный клиент выбирает Prybar и запрашивает покупку через настоящий ProfileAction.
4. Ошибка adapter блокирует запись. Runner вызывает те же `ProfileService:remove/add`, что обработчики PlayerRemoving/PlayerAdded, для одного настоящего Player/UserId. Он не разрывает сетевое подключение клиента. Проверяет статус восстановления, запрет покупки и сохранённую очередь; сбой держится ещё 15 с для просмотра профиля [P].
5. После восстановления проверяются новый токен, 8 жетонов, единственный титул, мастерство/история/Loadout. Повтор покупки не списывает жетоны. Следующий release теряет ответ; два быстрых переподключения профиля вновь дают Ready. Затем shutdown освобождает lease и запрещает новое открытие.
6. Требуется маркер `M4.1 STUDIO PASS`; предупреждения `profile close unconfirmed` ожидаются при намеренно введённом сбое. Это короткий engine-тест жизненного цикла, **не реальный сетевой reconnect, не полные матчи и не real DataStore**.

### Политика восстановления M4.1

`ProfileSessions` хранит текущее подключение отдельно от сохраняемой записи. `closing` — немедленный запрет новых операций, ортогональный состоянию записи; он выставляется до запуска асинхронного close. Новый токен не присваивается старой записи. Пока старый writer занят, новый вход ждёт без запуска второго writer. Все отложенные enqueue/flush/close в ProfileService используют ожидаемый токен; load проверяет актуальность подключения также внутри callback UpdateAsync. Устаревшие callbacks не публикуют статус и не освобождают новую lease.

| Событие | Переход и действие |
| --- | --- |
| Вход | Connection Recovering; Store Loading → Ready только после подтверждённого UpdateAsync |
| Выход | `closing=true`; очередь остаётся; close дожидается текущего writer и атомарно сохраняет batch/освобождает lease |
| Ошибка/timeout close | Store Unavailable + closing; новый connection остаётся Recovering; повторяется тот же batch с прежними sequence/receipts |
| Потерян ответ release | Callback сверяет актуальную запись; уже применённый batch не начисляется/не списывается снова |
| Подтверждённый release | Старый Store Closed; отдельное acquisition получает новый токен, данные читаются из хранилища |
| Истёк срок / другая lease | Старый writer получает LostLease; его операции **не переносятся** в новую lease. Новый load сверяет receipts/sequence; неопознанные операции помечаются unconfirmed в личном профиле |
| Чужая живая lease | Connection Locked; повтор без захвата; после release/истечения возможен обычный acquisition |
| Уход во время Loading | Acquisition отменяется; если ответ потерян после записи, отдельный close освобождает только собственный токен, без записи defaults |
| Shutdown | Новые подключения/награды запрещены, workers отменены, сохранения завершаются с общим бюджетом 25 с; любой отказ даёт false |

Один вызов хранилища имеет до трёх попыток (backoff 1/2 с + jitter до 0,3 с). Восстановление подключения длится до 180 с; между проходами паузы 1/2/4/8/10 с + jitter. Цикл матчей не ждёт эти операции. По исчерпании бюджета UI снимает признак повторов и предлагает войти позже; malformed/future schema прекращают повторы сразу. Отключённое по настройке Studio-хранилище не запускает бессмысленные повторы. Roblox-вызов, уже находящийся внутри API, не может быть принудительно прерван: поздний ответ остаётся ограждённым токеном, успех до его подтверждения не заявляется.

Очередь сохраняется в памяти до безопасного release. При подтверждённой потере lease она не переигрывается: UI сообщает количество unconfirmed, чтобы игрок проверил актуальную коллекцию/баланс/историю. Этот маркер и неподтверждённая очередь не переживают аварийное завершение процесса; M4.1 не обещает их восстановление после crash. Подтверждённые данные всегда читаются из хранилища, не заменяются старым кэшем/defaults. Награды раунда, начатого без Ready-профиля, задним числом не начисляются; следующий обычный раунд снова может давать прогресс.

**Обязательный release-gate перед M5 с Robux:** real DataStore smoke на отдельном опубликованном test experience/namespace, два запуска сервера, повторный вход, покупка/экипировка/награда, конкурирующая сессия и release. Пока нет доказательств этой проверки, Robux-монетизацию выпускать нельзя. Production-ключи для тестов запрещены. Это не блокирует технический M4.1.

## Исторические проверки исходного M4

## Автоматическая регрессия

Команды в README/Actions: неизменённые 46 M1 + 254 M2 + 87 M3, 99 progression/schema/catalogue и 38 store/failure assertions. Всего 524. Компиляция всех Luau, анализ pure-модулей и тестов, production/test Rojo, проверка состава production. Fake adapter находится только в tests и никогда не попадает в игру.

Store-тесты воспроизводят повтор callback UpdateAsync, throttle до записи, потерю ответа после записи, порядок операций во время yield, одновременные lease, истечение lease, аварийное завершение, повтор release, shutdown deadline, повреждённые/будущие схемы, миграцию v0 и попытку сохранить после неудачной загрузки. Последовательный номер защищает старую повторную запись даже после удаления её receipt из ограниченной истории.

## Автоматическая интеграция Studio

1. `rojo build studio-tests.project.json -o DoubleLife-M4-tests.rbxlx`. Открыть в Studio, F7 Server and Clients. Сначала добавить **одного** клиента. Main отключён только в этой сцене; Runner запускает Game с изолированным adapter.
2. Дождаться `M4 WAITING PASS: add FOUR clients now`, затем добавить **четырёх** в течение 240 с. Клиент уже проверил нулевой профиль, отсутствие XP за Waiting и отказы в покупке без средств/закрытом Loadout/клиентской команде Award. P открывает профиль, H/P закрывает. Не двигать персонажей во время автоматического сценария.
3. Первый состав ролей закреплён только тестом. Четыре клиента осматривают картину, физически участвуют в Music и проходят короткий маршрут; пятый остаётся AFK. Сервер проверяет реальное движение и разные виды действий. Смена Loadout в Active отвергается.
4. Шпион использует обычную отмычку: проверяются реальные закрытие окна после 14 с и исчезновение следа после 35 с. Кража и вынос завершают раунд обычным путём. Сохранённые XP/жетоны открывают альтернативы, AFK остаётся без награды. Повтор RoundFinished не меняет статистику.
5. В Results клиент выбирает Prybar для будущей роли, другой — JournalLens. Победитель покупает титул: adapter сначала фиксирует транзакцию, затем теряет ответ. Повтор не списывает второй раз. Экипировка титула и баланс проверяются после release/load профиля с новым lease для **того же подключённого клиента**. Это перезагрузка профиля через retained adapter, не новый процесс Studio и не real DataStore.
6. Во втором составе роли меняются. Сохранённый Prybar даёт окно 22 с/след 70 с, прежние права и GuardPolicy. Лупа показывает только факт давности 40 с и блокирует частое чтение. Council большинства возвращает досье и задерживает шпиона, след и таймеры корректно переживают паузу.
7. Ждать `M4 SECOND ROUND: waiting for genuine configured defender timeout`. Второй раунд проходит настоящие 1200 с активного времени плюс обычные 25 с Council, без ускорения. Автосохранения продлевают lease. Защитники побеждают по времени; активные клиенты получают вторую запись истории и мастерство новой роли; один голос AFK не даёт награды.
8. Следующий мир очищает сессионные события, но сохраняет профиль. Старый RoundFinished не меняет новую сессию. StoreAudit вызывает shutdown/освобождение lease, повторно загружает профили и печатает компактные данные аккаунтов. Итог: **`M4 STUDIO SUITE PASS 5 real clients ... real DataStore NOT TESTED`**. При FAIL смотреть конкретный маркер/trace; не считать неполный сценарий успешным.

Тест использует настоящие клиентские ProximityPrompt/RemoteEvent и Humanoid; некоторые переходы персонажей переставляются для сценария. Награды не подставляются в профиль. Клиент проверяет приватность ролей, отсутствие серверных модулей и внутренних lease/receipt в репликации. Это автоматическая интеграция, не ручная оценка баланса.

## Отдельная real DataStore проверка (не заменяется fake)

Нужен отдельный **опубликованный тестовый experience**, не production. Владелец настраивает Studio API Services только в нём; Roblox предупреждает, что Studio обращается к данным опыта. В `PersistenceSettings` установить `studioEnabled = true` и точный ненулевой test universe ID. `studioStoreName` обязан отличаться от live namespace. По умолчанию обе настройки закрыты, обычная локальная сцена продолжает играть без постоянных наград.

Запускать production-сцену в этом тестовом опыте (без M4Tests/MemoryStore). Получить подтверждённую награду и покупку реальным аккаунтом; остановить сервер; повторно запустить и сравнить XP, жетоны, коллекцию, экипировку, историю. Проверить второй сервер и истечение аварийного lease, не сбрасывая ключ вручную. Сохранить namespace, universe, время двух запусков и обезличенный результат. Только после этого отмечать real DataStore PASS. Отсутствие подходящего изолированного опыта отражается как NOT TESTED.

## Политика восстановления и будущая ручная приёмка

- При ошибке загрузки, неизвестной версии или активном чужом lease — не выдавать defaults как сохранённый профиль; матч работает, покупки/награды отключены. В исходном M4 требовался новый вход; M4.1 использует ограниченную автоматическую политику выше. Испорченные данные требуют отдельного восстановления, автоматически не обнуляются.
- При временной ошибке записи — сохранить принятую очередь, блокировать новые операции, повторять тот же batch. Если lease истёк/сменился, старый сервер больше не пишет. Неподтверждённые операции в оперативной памяти могут быть потеряны при аварии; уже подтверждённые покупки/награды не повторяются.
- Ручная оценка после сборки игры: интерес progression-loop, награды за разные роли, анти-AFK пороги, компромиссы инструментов, читаемость профиля/карточек на малых экранах, реальная сеть. Robux/монетизация, полный античит и экономическая балансировка в M4 не входят.
